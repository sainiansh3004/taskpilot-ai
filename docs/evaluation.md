## 2. Rubric Mapping: The 8 Core Evaluation Criteria

| Rubric Criterion | Evaluator Question | TaskPilot AI Implementation & Defense | Code / Artifact Proof |
|---|---|---|---|
| **1. Autonomy** | *Can the system determine and execute meaningful next actions without being told every individual step?* | The operator inputs solely a high-level natural language goal. TaskPilot AI independently synthesizes a multi-step plan (`plan_created`), selects the appropriate tools sequentially, inspects intermediate outputs, and advances subgoals without manual step intervention. | `backend/src/agent/orchestrator.ts:startTask()` & `backend/src/llm/autonomousDeterministicProvider.ts` |
| **2. Execution** | *Does the system actually perform work rather than merely explain what should be done?* | TaskPilot AI does not output conversational advice or hypothetical steps. It triggers real REST API invocations, drives a headless Playwright Chromium instance, extracts HTML DOM tables, parses local filesystem documents, and commits validated records into a persistent SQLite ledger. | `backend/src/tools/` (17 real tools) & `backend/src/browser/browserController.ts` |
| **3. Reliability** | *How does it handle unexpected states, errors, retries, and failures?* | Handles transient errors (HTTP 500, network timeouts) via exponential backoff retries with jitter (up to 3 attempts). Detects infinite loops via call-signature hashing (halts if an action repeats 3 times without progress). Halts safely on corrupt states (missing required fields, duplicate records) rather than polluting storage. | `backend/src/agent/orchestrator.ts:L330-L360` (Loop guard) & `L445-L478` (Retry engine) |
| **4. Verification** | *Does it determine whether the requested outcome was actually achieved?* | Completely decouples verification from LLM self-reporting. An independent `VerificationEngine` queries persistent SQLite storage directly and certifies 5 postconditions: record existence, exact vendor name, amount matched to the cent, due date match, and latest invoice ordering. Emits an audit scorecard with real record IDs and visual screenshots. | `backend/src/verification/engine.ts` |
| **5. Generalization** | *How much of the system can remain unchanged when given a different task?* | The entire orchestrator, tool registry, budget bounds, loop detector, and LLM abstraction remain 100% unchanged across different workflows. Tested and proven across 6 distinct scenarios: financial intake, duplicate interception, missing field handling, human-in-the-loop clarification, document parsing, and browser UI automation. | `backend/tests/orchestrator.test.ts` & `docs/demo-script.md` |
| **6. Engineering Quality** | *Architecture, implementation, code quality, debugging, and technical judgment.* | Modular TypeScript monorepo with 3 workspaces (`backend`, `simulated-company`, `frontend`). Strict typing (TypeScript 5.7), Zod runtime validation on every tool input, WAL-mode SQLite persistence, Server-Sent Events (SSE) streaming, 21 passing Vitest automated tests, and zero linter/compiler errors. | Root `package.json`, `tsconfig.base.json`, `tests/` |
| **7. Product Thinking** | *Does the solution focus on accomplishing the user's actual objective?* | Built with enterprise safety realities: Consequential write actions pause for operator approval (`REQUIRE_APPROVAL_FOR_WRITES`), ambiguous entities prompt interactive clarification, visual screenshot evidence is captured for human audit, and truthfulness is enforced over hallucinated completion. | `backend/src/tools/workflowTools.ts` & `frontend/src/components/ApprovalDialog.tsx` |
| **8. Technical Understanding** | *Can you clearly explain why you built the system the way you did?* | Complete architectural documentation in `docs/architecture.md` and detailed engineering trade-offs in `docs/design-decisions.md` (e.g. SQLite WAL vs Postgres for portable evaluation, Dual LLM engine for zero-cost offline reproducibility, SSE over WebSockets for audited telemetry). | `docs/architecture.md` & `docs/design-decisions.md` |
